# 0.4.1 blink app benchmark

Status: **Existing Android evidence, separated from offline model results**

Date: 2026-08-27

Production code changed: **No**

## Device and measured boundary

- Device: Samsung SM-G781B, Android 13/API 33
- SoC reported by Android: QTI SM8250 (`kona`)
- Delegate: CPU
- Camera analysis image: 480×360 RGBA
- Active target: 10 analyses/second

`FACE_PERF` starts immediately before `analyzeRgbaForRuntime` and ends after
normalization and blink/cheek state update. It includes RGBA bitmap allocation
and copy, rotate/mirror, MPImage creation, Face Landmarker inference, blendshape
extraction, signal normalization, and the state machine. It excludes delivery
before the CameraX callback and UI/AAC work after the state update.

## Functional app outcomes

| Physical run | Intentional recall | Activation precision | Negative sequences |
| --- | ---: | ---: | ---: |
| Full rig | 5/6 = 83.3% | 5/5 = 100% | 4/4 |
| Focused blink | 3/4 = 75.0% | 3/3 = 100% | 2/2 |

The focused run used a calibrated hold threshold of 1,419 ms. Its three
successful events activated at measured hold durations 1,466, 1,467, and 1,467
ms: 47–48 ms after the threshold. The failed `blink_slow_continuous_02` rig case
used an artificially slowed public blink video. It ended at 1,533 ms with
`WeakClosure`, 114 ms after the threshold, because a weak/open observation is
processed before duration activation. This is an app state-machine stress case,
not a model benchmark or a test of user agility. The available telemetry cannot
identify the exact camera-delivery gap
or assign it to one pipeline stage.

The measured analysis block averages about 39 ms and peaks below 78 ms on this
device. Therefore the previously observed 176 ms uncertainty window is not
explained by Face Landmarker compute alone. Camera delivery, cadence gating,
scheduling, and discarded frames remain unmeasured contributors.

## Coverage limits

This is one Qualcomm SM8250 device. It does not establish MediaTek or Samsung
Exynos behavior, low-end-device latency, thermal throttling, or GPU/NPU behavior.
No hardware-specific optimization decision should be based on it.

## QA telemetry defect found during this audit

The rig's `cheek_performance_samples()` parser and its unit test still expect
`CHEEK_PERF path=rgba-mediaimage`. Production has emitted
`FACE_PERF path=mediapipe` since blink and cheek began sharing the analyzer.
Consequently recent run JSON silently records an empty `cheek_performance` list
even though timing lines are present in the logs. `docs/OPTICAL_RIG_TEST.md` also
names the obsolete tag.

This defect affects automatic benchmark collection and documentation, not face
detection behavior. It is documented here and intentionally left unchanged for
discussion rather than being fixed as an unrelated hidden edit.

## Verdict

The app evidence is insufficient for release confidence because one artificial
state-machine stress case failed. Inference cost is not the dominant explanation
for the reproduced miss; model score stability, frame delivery, and the
precision-first state transition remain separate hypotheses. Per-stage and
camera-to-decision instrumentation is needed
before attributing the 176 ms gap or optimizing production code.
