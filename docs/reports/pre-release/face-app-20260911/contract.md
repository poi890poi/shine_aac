# Visible-app camera backend comparison

Type: performance research and test tooling. Baseline revision 0ac8ba0. The user approved this phase after reviewing the six-condition native replay screen. Keep CPU as the product default; any promotion requires new evidence.

Compare debug preview CPU and GPU APKs built from the same source with profiling enabled equally. The only intended candidate difference is the existing debug manifest delegate selection. Preserve preprocessing, resolution selection, sampling cadence, model, calibrated thresholds, native owner-thread and input lifetime rules, CPU fallback, and AAC behavior. Restore the original installed preview APK and exact app/display preferences after testing.

Runtime may use camera images, monotonic capture timestamps and the selected session calibration. It must not receive stimulus identities, expected events or host timings as inference inputs. Only declared licensed stimuli from testdata/optical-rig/sources.json are permitted. Rig geometry must show the whole face with margin at approximately 70% preview height. Revalidate geometry before using a saved fixture; create calibration on CPU when necessary and keep that identical calibration for the GPU comparison. Personal calibration is not overwritten permanently.

Admission sequence: confirm acknowledged device window and leases; verify baseline device acceptance and optical framing; run short CPU/GPU/CPU/GPU or counterbalanced ABBA physical gesture comparisons with identical fixture configuration. Reject any backend mismatch/fallback as a GPU comparison, failed independent gesture case, unusable framing, unverified app visibility, lost event identity or inconsistent timestamp accounting. Preserve failures and do not relax thresholds to admit a candidate.

If admission passes, run alternating CPU/GPU sessions for at least 30 continuous minutes per condition and device. Aim for two observations per backend, with order reversed; start with the tablet and prioritize the phone tail-latency comparison. Extend to 60 minutes when thermal trends remain rising and the device window permits. Do not pause or cool inside a timed session. Stop elevated thermal runs as incomplete evidence; retain the reason. Match starting battery temperature within 1 C of discovery, require at least three minutes of display-off cooldown, and keep charging/display settings identical. A battery-temperature match does not establish matched SoC or ambient temperature.

Record actual backend, image dimensions, calibrated fixture identity, fresh accepted results, missing/unusable input, longest gaps, per-frame pipeline stages, camera-result age, observed activations, app window focus/awake state, UI frame timing, thermal status/sensors, memory and process CPU. Frame age is camera-to-classifier timing only if the timestamp clock is verified; it does not include visual/audio feedback. Independent optical/UI evidence is required for activation correctness and feedback latency. Never infer per-frame percentiles from averaged log windows or fresh output from retained state.

Decision criteria: no missed, false or duplicate activation increase on the predeclared cases; no more than 10% late/early p95 degradation; no material UI responsiveness regression. A candidate requires a consistent direction of benefit across counterbalanced sessions and an improvement exceeding baseline repeat variation. Inspect maxima and p99 separately; one outlier is not a repeatable tail improvement. No runtime backend default changes from a single successful run. Include a fresh timing holdout after candidate definition when practical; repeated known actors do not establish unseen-user accuracy.

USB-powered battery counters cannot establish whole-device energy. An external power meter or supported validated rail measurement is required for an energy claim. Record unsupported measurements as unknown. Camera, preview and AAC activity distinguish this phase from the earlier native replay screen; optical/device gates remain distinct from a full release.

Before physical claims, use device-test.bat; camera/detector checks use optical-rig-test.bat on the interactive desktop. Both run inside acknowledged shared leases. Keep leases through exact settings/APK restoration and display-OFF verification, including failures. Explicitly release the device window at completion. No unrelated workspace changes are included.

The continuous workload is defined before its pilot: one visible normal AAC board process, the existing six-column public demo profile, 30 seconds of relaxed-face warmup, then fixed 15-second cycles. Five-second deliberate closures alternate with 350-ms short-blink controls, rotating the three already declared public closed poses (0.25, 2.0, 3.0 s). The remaining cycle is relaxed face. Expect exactly one activation on each deliberate cycle and zero on each control; no retries or feedback-dependent extensions. A short pilot must pass before the same workload is lengthened. Record acknowledged presentation intervals and retain any late host deadline as an incomplete run. These repeated known poses are a sustained workload, not evidence of unseen-user accuracy.

The product cadence is 100 ms for active long blink, 66 ms for active cheek, and 200 ms in power-saving idle. Blink live-app throughput must therefore not be equated with the earlier 66-ms native replay workload. The new continuous blink harness leaves that 100-ms policy intact. Backend comparisons within each gesture use the same policy.

The new host-only collector pairs per-frame stages and completion records by process, camera timestamp and actual backend. It retains event identities across overlapping reads and rejects missing identities/conflicting records. Timing summaries use the device-epoch completion window; early/late windows use elapsed capture time rather than frame counts. Same-process camera/model reinitialization also invalidates continuous-session evidence. No classifier-held state is observable in this telemetry, so it is reported unknown rather than fresh. Sample focus/awake/thermal state every cycle; those samples do not prove visibility at every instant. UI timing from Android gfxinfo and start/end screenshots does not establish every visual defect or physical stimulus-to-render latency.

Camera clock admission uses the selected camera's HAL metadata, requiring SENSOR_INFO_TIMESTAMP_SOURCE_REALTIME. Android documents that REALTIME timestamps share SystemClock.elapsedRealtimeNanos; UNKNOWN cannot establish that comparison. Source: https://developer.android.com/reference/android/hardware/camera2/CameraCharacteristics.html#SENSOR_INFO_TIMESTAMP_SOURCE. USB power remains an explicit limit on energy conclusions.

Diagnostic amendment after the first cheek pair: GPU emitted one native activation on `cheek_surprise_negative`, while CPU emitted zero. GPU admission and sustained testing stop. Run a bounded CPU/GPU/CPU/GPU confirmation, two independent repeats of that same predeclared negative per run, using the frozen CPU fixture and unchanged APKs. Retain each failed result; a test-failure exit is an observation for this diagnostic, never admission. Cleanup failure, backend mismatch, missing evidence or device failure still stops the sequence. This tests whether the association repeats or also affects CPU; it does not change thresholds or redefine the negative label.

Independent-work amendment while GPU admission is blocked: rerun the phone's full baseline device acceptance with CAMERA temporarily granted, restoring its originally ungranted state. Pilot the continuous workload on the tablet CPU APK for 60 seconds. If that pilot passes, a 30-minute CPU-only reference may proceed with the same fixed workload, starting-temperature and cleanup rules. This is harness validation and a baseline observation, not an admitted CPU/GPU sustained comparison. The original GPU failure remains in the decision record even if later negative-control repeats pass. No GPU sustained run or default promotion is authorized by the CPU-only reference.
