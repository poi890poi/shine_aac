## 1. Purpose and decision

This plan validates the v0.4.1 ABI packaging, shared MediaPipe face analysis, and
plain camera-action wording through complete AAC and helper workflows. It follows
`docs/TESTING_PLAN.md`, `docs/DEVICE_ACCEPTANCE_TEST.md`, `docs/LAYOUT_QA.md`,
`docs/OPTICAL_RIG_TEST.md`, and `docs/RELEASE_PROCESS.md`.

The release decision is based first on meaningful communication and setup journeys.
Focused gesture repetition, page cycling, and geometry inventories are supporting
stress evidence only; they cannot substitute for those journeys.

## 2. Scope and principal risks

| Risk | Change | Required evidence |
| --- | --- | --- |
| R1 | APKs are now split by ABI | One correctly named APK per supported ABI, no universal APK, correct native libraries, ARM64 install/upgrade on the physical phone, x86_64 emulator install when available |
| R2 | Long blink moved from ML Kit to MediaPipe | First-use offline availability, calibration, normal-use communication, natural/short-blink rejection, reopen and repeat behavior |
| R3 | Blink and cheek movement share one analyzer/model | Switching actions without restart, no cross-action stale state, bounded latency/memory, correct lifecycle release/reacquisition |
| R4 | Cheek movement must work before personal setup | Fresh-install activation without registration; optional setup succeeds from automatically found samples and never requires six prior activations |
| R5 | Face framing targets about 70% | Whole face visible with margin; near-full-frame input rejected with useful guidance |
| R6 | Terminology and Offline resources changed | Helper can find Camera actions / 相機動作 and Cheek movement / 臉頰動作; no duplicate face-detector resource; text fits supported layouts |
| R7 | Privacy/data-safety claims changed with ML Kit removal | Dependency and packaged-artifact inspection finds no ML Kit; current policy and Play documents describe bundled on-device MediaPipe processing |

Out of scope: clinical suitability, fatigue over hours or days, and claims about an
intended AAC user's comfort. Those require a supervised user/helper pilot and remain
open even if this engineering plan passes.

## 3. Scenario design rules

1. Every normal-use case has a role, goal, meaningful final state, and observable
   outcome. “Page opened,” “page scrolled,” and “gesture detected” are intermediate
   observations, not outcomes.
2. Configuration is opened only to save a change, cancel a change, complete setup,
   recover from a problem, or inspect information needed for a stated decision.
3. A page is scrolled only to reach a named control or information item used in the
   scenario. The target and subsequent outcome are recorded.
4. A normal-use optical session must compose and speak useful messages, include a
   correction, and preserve or clear text for a reason. Repeated open/close stimuli
   run only after the normal-use sessions and are labeled detector stress.
5. Blink and cheek sessions use different communication tasks. Replaying the same
   arbitrary sequence twice does not establish broader usability.
6. Automated optical media must be checksum-verified public material declared in
   `testdata/optical-rig/sources.json`. User uploads and private face captures are
   prohibited. The whole face remains visible at approximately 70% preview height.
7. Harness setup, preference injection, state restoration, and evidence collection
   are identified as harness operations and excluded from user-task counts.
8. If production source changes after testing starts, rerun every case whose risk or
   artifact can be affected. Never combine evidence from different APK hashes.

## 4. Roles and environments

### Test roles

- **AAC user — long blink:** uses a deliberate long blink while natural blinks must
  remain quiet.
- **AAC user — cheek movement:** has a repeatable cheek action but no existing personal
  model on first use.
- **Helper:** selects the input, positions the camera, adjusts timing, handles
  permission/recovery, and confirms the result with the AAC user.

Automated media simulates only the camera signal. Reports must not call it a real-user
comfort or fatigue test.

### Environment matrix

| Environment | Purpose |
| --- | --- |
| Physical ARM64 Samsung phone, Android 13/API 33 | Required install, lifecycle, native UI, camera, and optical evidence |
| Visible interactive Windows `Default` desktop and monitor rig | Required physical optical path; atlas decode proves monitor visibility |
| x86_64 phone/tablet emulator, if available | ABI-install and large-screen/layout coverage; not detector proof |
| Phone portrait plus constrained landscape/tablet viewport | Layout and wording coverage |
| `zh-TW` and English; default and 200% font scale | Localization, accessibility, and clipping coverage |
| Network available and airplane/offline state | Resource/update behavior and first-use offline camera actions |

Physical UVC coverage is required before claiming UVC release readiness. If no UVC
camera is available, record that as an open coverage gap rather than a pass.

## 5. Entry criteria

- The intended source commit is recorded and the working tree is clean.
- `version.properties` identifies the candidate as 0.4.1 with version code 61.
- The physical device ABI, Android version, battery temperature, free space, installed
  signature, and existing app-data preservation decision are recorded.
- Public optical sources pass license/source/checksum validation.
- The phone and monitor are fixed at comfortable geometry; the decoded face occupies
  roughly 70% of preview height and never fills the preview.
- Original app preferences and camera selection are captured for restoration.
- No release result is recorded until all evidence references one exact APK SHA-256.

## 6. Ordered test cases

### Harness preparation before execution

The current harness must be adjusted before it can execute this plan faithfully:

| ID | Required harness change | Acceptance |
| --- | --- | --- |
| H01 | Update build/package discovery for ABI-specific APK outputs | It selects the APK matching the recorded device ABI and never silently falls back to another output or a universal APK |
| H02 | Replace the one shared `PHYSICAL_NORMAL_USE_SCRIPT` replay with distinct J03 and J04 task manifests | Blink and cheek reports show different goals, messages, corrections, and final outcomes |
| H03 | Refactor the native Configuration audit into saved-change, canceled-change, resource-information, recovery, and layout cases | Navigation-only inventory remains structural coverage; it is not reported as a completed user journey |
| H04 | Require every scripted scroll to name its target control/information and verify the resulting decision or state change | A scroll without a target/outcome fails harness validation instead of adding coverage |
| H05 | Separate normal-use, focused detector, lifecycle stress, and harness setup counts in reports | Repetition and page cycling cannot inflate functional/UX case totals |
| H06 | Add test-manifest fields for role, goal, start state, expected message/outcome, source provenance, and cleanup | A case with missing semantics or provenance is rejected before device interaction |

Harness changes receive their own unit/static tests. They are infrastructure needed to
collect honest evidence; they do not count as product PASS results.

### Phase A — deterministic and package gates

| ID | Goal and meaningful outcome | Method | Pass criteria |
| --- | --- | --- | --- |
| A01 | Establish source integrity before user testing | Record commit, dirty state, version, dependency graph, and changed-file inventory | Intended commit recorded; no unexplained files; candidate version correct |

### Phase B — meaningful helper and AAC journeys

#### J01 — First-use cheek movement, offline, without personal setup

**Role/goal:** A helper enables camera input for an AAC user who can move their cheek;
the user needs to ask for water immediately, without registering examples first.

**Starting state:** Fresh app data, network disabled, no saved camera model or camera
permission.

**Actions:**

1. Open Configuration to change Switch input to **Camera actions / 相機動作**, then
   save and verify that the chosen input is active.
2. Open **Camera actions**, grant permission, select **Cheek movement / 臉頰動作**,
   position the whole face near 70%, and choose Done without starting personal setup.
3. Use cheek movement through the normal scanner to compose and speak a water request.

**Pass:** No download/model-wait state appears; no prior successful activation or six
registrations are required; the spoken message matches the composed request; every
deliberate action produces at most one activation; rest intervals remain quiet.

**Evidence:** Fresh-state preferences, offline state, setup screenshot, framing metric,
activation log, final message, speech event, and before/after UI state.

#### J02 — Optional personal cheek setup from automatically found samples

**Role/goal:** The helper personalizes cheek movement because the default response is
not selective enough.

**Starting state:** J01 completed; camera geometry unchanged.

**Actions:** Open Camera actions for the explicit purpose of personal setup. Record the
resting phase, present one clear public cheek-action sequence with natural recovery,
and complete the practice confirmation.

**Pass:** Setup can produce a new complete model from automatically clustered samples;
the UI never waits for six runtime activations; progress and invalid-framing reasons are
visible; the saved model timestamp changes; the intended action is accepted in practice;
frown and surprise controls remain quiet.

**Evidence:** Public source id/license/checksum, setup timeline, model record, preview
and 70%-framing captures, practice result, and negative-control counts.

#### J03 — Long-blink daily communication with correction

**Role/goal:** A long-blink user communicates several daily needs and corrects one
mistake without helper editing.

**Starting state:** `zh-TW`, long blink selected and personally set up, normal scan
timing, empty message.

**Tasks:**

1. Compose and speak **幫忙喝水**.
2. Clear because the first communication turn is complete; compose and speak
   **不舒服休息**.
3. Start a pain/help request, intentionally choose one wrong visible suggestion, use
   **復原**, finish the intended request, and speak it.
4. Enter English through **EN**, compose and speak **HI**, clear after that turn, and
   return through **注音**.

**Pass:** Four intentional speech turns complete through the normal board; correction
restores the right page/message; natural blinks while reading or waiting do not select;
no missed or duplicate deliberate activation occurs; clear is used only between
completed communication turns.

#### J04 — Cheek-movement communication with different needs

**Role/goal:** A cheek-movement user communicates needs different from J03 so the
second detector path is not validated by replaying the same script.

**Tasks:** Use paths first proven reachable by deterministic board tests to communicate
and speak: a toilet request, a repositioning/help request, a tired/comfort message, and
an English **OK** acknowledgement. Include one wrong choice and **復原**, and clear only
after a completed speech turn.

**Pass:** Four useful turns complete with the saved cheek setup; ordinary smiling,
speaking, and resting between turns do not activate; no action produces duplicates.

The exact visible token sequence must be captured before execution and must use normal
board/suggestion paths—no test-only vocabulary or direct message mutation.

#### J05 — Configuration change with a visible consequence

**Role/goal:** A helper adapts the device for slower access and dark surroundings.

**Actions:** Open Configuration, change scan timing and contrast theme, save, then
verify changed scan cadence and board appearance. Reopen, change one value, cancel,
and verify the canceled value did not persist. Open Offline resources to answer whether
camera actions work offline and verify that one **Face-action model / 臉部動作模型**
entry covers blink and cheek movement.

**Pass:** Saved changes visibly apply; canceled changes do not; the page has no duplicate
long-blink/cheek detector entries; no old 光學開關 or 臉頰抽動 label is visible. Every
scroll has a named target used by the scenario.

#### J06 — Interrupted request and camera recovery

**Role/goal:** The user begins a help request, is interrupted when the helper checks
another app or the screen sleeps, then finishes without losing work.

**Actions:** Compose the first part of a request, background/foreground the app, repeat
with display off/on, then complete and speak the request through the selected camera
action.

**Pass:** Draft and repair history survive; camera is released while inappropriate and
reacquired on return; no phantom activation occurs; the request is completed once.

#### J07 — Idle wake without accidental selection

**Role/goal:** The user resumes a paused communication session after the configured
idle interval.

**Actions:** Preserve a non-empty draft, stop scanning, wait for idle/power-saving state,
perform one camera action to wake, then a later action to continue scanning.

**Pass:** The first action only wakes; message and selection are unchanged; the second
action resumes normal selection; camera status returns from power saving to active.

#### J08 — Camera change for a mounting need

**Role/goal:** The helper changes cameras because the original angle cannot show the
whole face comfortably.

**Actions:** Change to another built-in camera or a real UVC camera, restore about 70%
framing with normal zoom controls, save, leave setup, and complete one short spoken
request.

**Pass:** Selection persists; preview and overlay align; no stale analyzer state from
the prior camera appears; the request succeeds. With UVC, disconnect/reconnect and
permission recovery must also be demonstrated.

#### J09 — Large-text helper setup

**Role/goal:** A helper using enlarged text must still configure and verify camera input.

**Actions:** At 200% font scale, find Camera actions, select each action, adjust the hold
value once for a stated reason, inspect framing guidance, and finish setup.

**Pass:** Critical actions, preview, action names, values, Start, and Done remain visible
and tappable; no clipping/overlap; preview remains at least 50% of portrait height;
secondary scrolling is discoverable and reaches the intended control.

### Phase C — focused safety and stress, after journeys

| ID | Explicit hypothesis | Method and limit | Pass criteria |
| --- | --- | --- | --- |
| S01 | Natural facial behavior must not select | Replay natural blink, short blink, smile, surprise, and frown controls during realistic rest/read intervals | Zero activations for every negative case |
| S02 | One sustained action must not run away | Hold one long blink through block → first row → first cell | Exactly one native activation, bounded first-leaf advance, no repeat until release |
| S03 | Detector must re-arm after recovery | Present two deliberate actions separated by a verified open/rest interval | Exactly two activations with a release between them |
| S04 | Positive reliability is stable | Repeat each selected positive case 10 times after normal-use passes | Ten expected single activations, zero miss/duplicate; timing and thermal state recorded |
| S05 | Camera lifecycle does not leak | Three explicit cycles: change camera and return; background during setup and resume; open setup then finish a request | Camera released/reacquired correctly, draft/settings preserved, bounded PSS, no crash/ANR. This is stress evidence, not three UX journeys |
| S06 | Near-full-frame geometry is unsafe | Present an otherwise valid face above the accepted size boundary | No calibration/runtime acceptance; visible instruction asks for more distance/approximately 70% framing |

### Phase D — layout, compatibility, and artifact review

- Run the required locale/theme/font/viewport matrix from `docs/LAYOUT_QA.md`.
- Capture board, Configuration, Input Test, Offline resources, Camera actions,
  permission recovery, and App Info with system navigation visible.
- Check 48dp targets, system-bar insets, clipping, overflow, preview share/stability,
  concise labels, dark surfaces, and action/state differentiation.
- Run one phone and one tablet-class configuration; clearly label emulator-only tablet
  evidence.
- Package the candidate split APK set and signed AAB before physical testing, freeze
  their hashes, and use the versioned ARM64 APK for every physical journey and gate.
  Record filenames, bytes, SHA-256, signing identity, embedded version, and ABI.

## 7. Execution order

1. Resolve entry blockers, especially 0.4.1 version metadata.
2. Implement and review H01–H06 without running physical/product acceptance cases.
3. Run deterministic source/unit checks A01, A02, and A06.
4. Build and package the versioned split APKs and signed AAB through A03 and A04. Freeze
   their hashes; do not rebuild or substitute them during the remaining plan.
5. Install the exact versioned ARM64 APK through A05.
6. Run fresh-state J01 before any personal model is created.
7. Run J02, then J03 and J04. Normal-use journeys must precede focused repetition.
8. Run J05–J09, then S01–S06.
9. Run layout/compatibility review and `device-test.bat` against the exact frozen APK.
10. Run the full interactive `optical-rig-test.bat` gate against that same installed APK,
   using only public sources.
11. Re-verify every frozen artifact without rebuilding, then write the pre-release report
    with PASS/FAIL/OPEN per case and a release decision. Any source/resource change or
    artifact rebuild invalidates the affected evidence and restarts the relevant gates.

## 8. Evidence and reporting

Each case records:

- commit, version, artifact path/name, SHA-256, signing identity, ABI, device, OS;
- role, goal, starting state, exact saved/canceled setting changes, and final outcome;
- selected labels, final message, speech turns, correction/clear reason, camera action
  count, misses, duplicates, false positives, and elapsed time;
- public optical source metadata and measured face occupancy when camera media is used;
- screenshots/UI XML at meaningful state transitions, not arbitrary intervals;
- thermal state, crash/ANR review, and linked raw logs;
- cleanup and proof that original preferences were restored.

Results use **PASS**, **FAIL**, **BLOCKED**, or **OPEN COVERAGE GAP**. A failed product
assertion is not renamed “infrastructure.” An uncertain visual/optical result preserves
evidence for review and is not silently treated as a pass.

## 9. Release acceptance

The candidate may proceed only when:

- A01–A06 and J01–J09 pass, except explicitly documented unavailable-hardware coverage;
- no unresolved P0/P1 finding remains;
- long blink and cheek movement each complete their distinct normal-use journey before
  focused replay is considered;
- first-use cheek movement works offline without prior setup;
- optional cheek setup does not require six prior activations;
- all negative controls produce zero activation and all required positives produce the
  exact expected count;
- the physical device and optical rig gates pass on the exact packaged artifact;
- ABI artifacts, AAB, wording, privacy documents, and release metadata agree;
- fatigue, UVC hardware, tablet, or intended-user limitations are stated as open gaps
  rather than inferred passes.
