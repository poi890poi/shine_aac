# 0.4.1 blink backend comparison

Status: **Historical pre-fix comparison; not the current release verdict**
Date: 2026-08-26
Source history: `codex/archive-v0.4.1-pre-cleanup-20260827`
Compared implementation: `162583c` from the original candidate history
Device: Samsung SM-G781B, Android 13/API 33
Decision: **MEDIAPIPE BLINK RELIABILITY NOT YET RELEASE-READY**

## Result

ML Kit was exact on all 90 matched physical-camera sequences. MediaPipe was exact
on 89 of 90: it produced one false activation while replaying the public natural
blink control. Both backends detected every intentional activation and correctly
re-armed after paired gestures.

| Measurement | MediaPipe | ML Kit |
| --- | ---: | ---: |
| Exact sequences | 89/90 | 90/90 |
| Intentional activations | 60/60 | 60/60 |
| Quiet negative sequences | 39/40 | 40/40 |
| Paired-gesture recovery | 10/10 exact pairs | 10/10 exact pairs |
| Findings | 1 P1 false activation | none |

The MediaPipe failure is a detector/classifier result, not a board-oracle error.
The trace records `holdStart`, followed by `activate` with `longBlinkMs=801`, while
the public natural-blink stimulus was active.

## Matched method

Each backend used the same phone, rear camera ID `2`, 2.4x zoom, board transition
oracle, and checksum-pinned public stimuli. Each of nine cases ran ten times:

- four negative controls: natural blink, short blink, smile, and surprise;
- four single-activation long/slow blink positives;
- one recovery case containing two separate long blinks.

This produced 90 sequences per backend: 40 negative sequences, 40 single-positive
sequences, and 10 paired-recovery sequences. The paired cases raised the expected
intentional activation total to 60. The phone remained at Android thermal status
`LIGHT` during both runs (37.3 C for MediaPipe and 37.1 C for ML Kit).

Fresh native calibration preceded each backend run:

| Learned value | MediaPipe | ML Kit |
| --- | ---: | ---: |
| Slow blinks measured | 5 | 5 |
| Rest false positives | 0 | 0 |
| Hold duration | 698 ms | 795 ms |
| Close threshold | 0.483 | 0.542 |
| Reopen threshold | 0.227 | 0.120 |
| Reopen stability | 168 ms | 133 ms |
| Saved quality | good | good |

## Runtime and package cost

| Measurement | MediaPipe-only | ML Kit blink + MediaPipe cheek |
| --- | ---: | ---: |
| ARM64 debug APK | 27,343,095 bytes | 40,652,215 bytes |
| SHA-256 | `3a732392846e1597d64da6ef83f056e6ead73f86e2cae3783de38fdbb50c99f2` | `d4cf14ad3f402fdff577d1bc4c80d1fe2efdfd457f2c44fbe00cbdac13123d43` |

The MediaPipe-only APK is 13,309,120 bytes (12.69 MiB, 32.7%) smaller than the
mixed-backend APK. MediaPipe logged 6,550 measured frames across 131 50-frame
windows: mean window average 36.17 ms/frame, median 39.30 ms, 95th percentile
41.87 ms, and maximum observed frame 74.96 ms. The ML Kit production path did not
emit equivalent inference timing, so this run cannot support a fair latency winner.

## Test-integrity note

After the comparison, the exact MediaPipe APK was restored on the phone. A planned
two-case restoration smoke was rejected as invalid because neither case produced
face scores. A subsequent atlas check decoded zero tags and confirmed that the
camera could no longer see the controlled Windows display. Those results are rig
visibility failures and are not included in the backend accuracy totals. Evidence:
`test-results/optical-20260826-193922/FINDINGS.md` and
`test-results/optical-20260826-194143/FINDINGS.md`.

## Recommendation

Do not ship 0.4.1 with the current MediaPipe blink behavior. First harden
natural-blink rejection and repeat this matched gate with zero false activations.
Do not add a second production backend solely from this run. The tested bundled
mixed-backend APK is 12.69 MiB larger; an on-demand ML Kit module has not been
implemented or measured. Reconsider that fallback only if MediaPipe remains
unreliable after focused correction and broader public-stimulus validation.

This deterministic comparison does not replace testing across real users,
eyewear, lighting, posture, fatigue, and camera mounting.
