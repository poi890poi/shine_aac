# Foreground state control

Proposed after the new foreground pilot's GPU serial p95 (43.5 ms in its first whole cycle) contradicted the older equivalent 320x240/66 ms GPU serial run (123.8 ms). Both native inference and preparation sped up, so preparation overlap alone cannot explain the difference. Older and newer initial AP temperatures were similar, but this is not proof of a cause.

Run the same GPU serial instrumentation with and without launching SettingsActivity, in ABBA order, once the sustained device sessions finish. Use a separate test APK; do not replace the immutable APK used by any sustained comparison. Keep one complete public timed cycle per run (15.378 seconds), compact timing records, same model/thresholds/cadence/telemetry and warmup. The short duration should avoid normal screen timeout, and every telemetry sample must verify interactive=true; otherwise mark the control confounded. Wake each run identically, preserve persistent settings and verify display-off cleanup after each run.

The single intended variable is the presence of a foreground Activity. Record /proc/self/cgroup after the optional Activity launch and Android interactive state every 10 seconds. Native process scheduling context is supporting evidence, not an estimator input or an accuracy metric. Run two repetitions per state in reversed order to reduce warming/order bias. Every positive/negative case must still pass; no threshold tuning. This is a short causal scheduling diagnostic, not a sustained thermal or energy test, and cannot prove equivalence to the full app's camera/rendering workload.

Also record keyguard/device-lock state and the Activity's window focus after warmup. A control requires awake, unlocked screen evidence, end-of-run interactive=true, and window focus for the Activity-present condition. Missing/false evidence marks the comparison confounded; do not infer foreground visibility from Activity launch alone. These extra state checks are in the separate control APK, not the immutable APK used for the sustained screen.

Reusable entry points are `scripts/run-face-foreground-benchmark.ps1` (acknowledged device window required; lease and display cleanup included) and `scripts/report-face-foreground-benchmark.py`. The report rejects incomplete ABBA sequences, differing artifact identities, failed individual gesture cases and missing context evidence. `scripts/test_face_sustained_benchmark.py::SustainedReportTest.test_foreground_control_requires_awake_evidence_including_end` exercises the awake, lock and focus rejection paths. Future comparisons intended to represent a visible AAC app must retain this scheduling-context evidence; Activity-absent timings are labeled diagnostic observations, never substituted for the visible-app baseline.

## Tablet timeout diagnosis and separately identified repeat

The first tablet ABBA batch passed gesture cases, but both Activity-absent runs recorded `endingInteractive=false`; their sampled screen states before the end were awake. Both Activity-present runs ended awake with verified focus. A leased, read-only diagnostic verified the unchanged screen timeout is 30,000 ms and final display OFF/Dozing. Model initialization, warmup and the 15.378-second replay together outlast that timeout; a window flag protects only the Activity-present condition. The original assumption that a short replay alone avoids screen timeout was incorrect. Preserve all four original runs as a rejected scheduling comparison.

Repeat only the tablet batch with a separate immutable test APK and distinct `foreground-awake` output names. Add an optional, test-only, 120-second screen-bright wake lock to **both** ABBA states, acquired before model setup and released in `finally`. Use temporary UiAutomation adoption of only WAKE_LOCK, then drop that identity; change no manifest grants or persistent display settings. Require the lock held at the end as well as the existing awake, unlocked, focus, artifact and gesture gates. This predicts both Activity-absent runs now end awake while their process groups remain distinct from Activity-present runs. Do not combine the rejected observations into the new timing comparison. The phone's original batch already passed all context gates; no phone repeat or cross-device equality of wake-lock method is claimed.

Android documents the screen-bright lock and explicit release requirement; its preferred window flag cannot cover this deliberate no-Activity test condition. The deprecated lock is limited to instrumentation and never added to the application. [PowerManager](https://developer.android.com/reference/android/os/PowerManager#SCREEN_BRIGHT_WAKE_LOCK), [UiAutomation permission identity](https://developer.android.com/reference/android/app/UiAutomation).

**Outcome: the wake-lock countermeasure failed.** Both repeated Activity-absent runs again ended non-interactive even though the lock object reported held. Reject the entire repeated comparison too; no tablet visibility ratio is accepted. The specific platform policy responsible for ignoring/overriding the held lock was not established. Preserve the failed APK, source and numeric evidence, and remove its ineffective option from active instrumentation/host runners. A held wake-lock object is not a substitute for measured screen state. The six sustained conditions used a visible Activity throughout and are unaffected; the phone's original control remains usable. The reporting gate continues to reject missing/false end-of-run awake evidence.
